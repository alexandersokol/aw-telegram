# Sync Cost (Task 11d) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an always-online laptop costs far fewer Firestore operations: a 30 s sync, no rewrite of
unchanged health and live documents, and no reads of days or alert state a sync doesn't use.

**Architecture:**
- Companion: `SYNC_INTERVAL = 30` in `sync.py`. Failure backoff keeps its 15 s base and floor and
  its 300 s cap. A receipt queued since the last request (accepted offer, shown or closed message,
  applied setting) is sent at the next step, so receipts are not slower than with 15 s. `ONLINE`
  in `status.py` becomes 90 s; the bot's `ONLINE_MS` follows, so both describe the same facts.
- Backend, `deviceApi.ts`: `sync/current` keeps, per observation kind, the latest accepted
  `{sequence, observedAt, digest}` (`observed.live`, `observed.health`). Ordering and the
  same-instant conflict check use it, so the documents keep their stored sequence when not
  rewritten. Live is rewritten only when it changes apart from `observedAt`. Health is
  rewritten when it changes apart from `observedAt` and `lastSuccessAt`, or when the stored copy
  is 5 minutes older than the new observation.
- `reports.ts` takes the live observation time from `sync/current` when it is newer, so "Зараз:"
  stays fresh while the app is unchanged.
- Reads: the `days` collection only with summaries; `alertStates` only when today's summary
  changed, the only case the sync evaluates alerts (settings changes evaluate them in the settings
  transaction; endtime alerts come from receipts). With no receipts and no summaries, the action
  snapshot reads controls, policy and parents only when an action is open.

**Tech Stack:** TypeScript, vitest, the Firestore emulator; Python 3.12, pytest.
