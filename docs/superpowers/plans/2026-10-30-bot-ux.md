# Bot UX (Task 11e) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** caregivers can always get back to the main menu, and the author of a settings change or
a clear learns when the laptop applied it, without re-checking.

**Architecture:**
- `withHome(reply)` in `TelegramBot.deliver` adds «🏠 Головне меню» (`nv:home`) to the first page
  of every reply that has no buttons and is neither a toast nor `bare`. `NavigationController`
  answers `nv:home` with `openMain` before any session lookup.
- Save replies say only what was saved, plus an offline line when `sync/current.serverReceivedAt`
  is absent or older than 2 minutes (`laptopOffline` in `reports.ts`, one read).
- `src/notices.ts`: a settings change that bumps the revision writes
  `appliedNotices/s-{revision}`, a clear writes `c-{revision}`. The sync transaction reads due
  notices only when an acknowledgement advances or an earlier sync left some (`noticesDue` in
  `sync/current`), groups them by author and enqueues one outbox event (`kind: 'applied'`) per
  active author, then deletes them.
- `WebhookAdmin.set` also calls `setMyCommands`; `info` also shows `getMyCommands`.

**Spec:** [2026-10-30-bot-ux-design.md](../specs/2026-10-30-bot-ux-design.md). Task:
implementation-plan.md, 11e.

## Global Constraints

- New copy goes in `bot/src/telegram/uk.ts` (11f moves it): `HOME_LABEL`, `APPLIED_PREFIX`,
  `OFFLINE_LINE`, `COMMANDS`, the clear save texts and the clear notice summaries.
- A notice is `{pairingId, userId, summary, createdAt}` plus `settingsRevision` or
  `cancellationRevision`, the field its kind is queried by. Each query is a single-field range
  (`<=` acknowledged revision, ordered, `limit(50)`), so no composite index. `userId` makes the
  recipient reference without reading parents.
- At most 50 notices per sync, merged by `createdAt`; any rest sets `noticesDue` for the next
  sync. Idle syncs (no advancing acknowledgement, nothing due) read nothing more.
- Authors not in `device.activeParentIds` get nothing; the outbox re-authorizes at send time, so
  a re-paired account gets nothing for its old pairing either.
- Notice writes count toward the sync's 450-write budget before action planning.
- Cleanup deletes notices older than the retention start; purge's recursive delete covers them.
- No sync contract or companion change. Backend-only deploy.
